# 로컬 DB 설계와 구현 규칙

## 적용 범위와 기술 방향

DB 구성, Entity·DAO·영속 저장 Repository, 트랜잭션, 동시성, 스키마·마이그레이션을 변경할 때 읽는다.
이 문서는 설계 기준이며 DB가 이미 구현되었다는 뜻이 아니다. 실제 구현과 버전은 소스·Gradle 설정으로 확인한다.

- Room KMP와 SQLite를 기본 방향으로 사용한다. 도입 시 현재 Kotlin·AGP·KSP 및 Android·iOS 타깃과의 호환성을 확인하고 안정 버전을 고정한다.
- Android·iOS에서 가능한 한 동일한 SQLite 동작을 사용하도록 bundled driver를 우선 검토한다. 구체적인 API는 도입 버전의 공식 문서로 확인한다.
- 카드·지출처럼 실제 연결하는 기능부터 구현한다. 미래 기능을 위해 테이블·공통 Base 클래스·동기화 엔진을 일괄 생성하지 않는다.
- 모듈 경계와 결과 계약은 [아키텍처](architecture.md)·[클린 아키텍처](clean-architecture.md), 플랫폼 설정은 [KMP와 빌드](kmp-build.md)를 함께 따른다.

## 책임과 데이터 흐름

- `core:data/commonMain`에 Database·Entity·DAO·Mapper·Repository 구현을 둔다. DB 파일 경로와 플랫폼별 생성 설정은 `androidMain`·`iosMain`에 둔다.
- DB와 Repository의 DI 정의는 구현을 소유한 모듈에 두고 `shared`에서 조립한다. 동일한 DB 파일의 인스턴스는 앱 수명에 맞춰 하나를 공유하며 화면마다 열고 닫지 않는다.
- `core:domain`은 업무 모델과 Repository 계약을 소유한다. Room 어노테이션·DAO·Entity·SQLite 예외를 domain 또는 feature 계약에 노출하지 않는다.
- Entity와 도메인 모델은 data의 순수 Mapper로 변환한다. Mapper 안에서 DB 조회·쓰기나 화면 상태 변경을 하지 않는다.
- 영속 데이터의 기준은 DB다. 저장 결과를 화면별 메모리 목록에 별도로 누적해 서로 다른 원본을 만들지 않는다. 입력 초안·포커스·저장 중 상태는 UI에서 관리한다.
- 조회는 필요한 범위의 `Flow`로 관찰하고 feature에서 `UiState`로 반영한다. 화면 상태·작업 취소·오래된 조회 결과 처리는 [MVI 규칙](mvi.md)을 따른다.

## 저장 형식과 무결성

- 금액은 원화 정수로 저장하고 부동소수점으로 변환하지 않는다. 개별 금액과 합계의 표현 범위를 구분해 오버플로를 처리한다.
- 거래 날짜처럼 시간대가 없는 날짜와 생성·수정 시각처럼 특정 순간을 구분한다. 날짜·월·시각의 저장 표현과 시간대·기간 경계 기준을 명시한다.
- ID는 안정적이고 변경되지 않아야 한다. 시간값이나 목록 위치를 식별자로 사용하지 않는다. 향후 공유 범위가 필요한 데이터는 가계부 식별자와 조회 범위를 설계 시 검토한다.
- 필수 값·기본키·외래키·고유성 등 저장 무결성은 가능한 범위에서 DB 제약으로도 보장한다. UI의 입력 검증만 신뢰하지 않는다.
- 고유 제약과 이름 비교 기준은 기능 정책에 맞춘다. 카드 별칭처럼 중복이 허용되는 값에 임의의 고유 제약을 추가하지 않는다.
- 조회 조건·정렬에 필요한 인덱스만 추가한다. 정렬은 동일 날짜·순서 값에서도 결과가 안정되도록 보조 기준을 정한다.
- 과거 기록의 표시값과 현재 관리 항목의 참조를 구분한다. 카드 삭제 후 지출의 카드 표시, 장보기 카테고리 변경 후 완료 기록의 이름 등 기존 보존 정책을 유지한다.
- 연쇄 삭제는 업무 정책이 허용하는 관계에만 적용한다. 관리 항목 삭제 때문에 과거 지출·완료 기록이 함께 삭제되지 않도록 한다.

## 트랜잭션과 원자성

- 함께 성공하거나 함께 실패해야 하는 읽기·쓰기는 하나의 DB 트랜잭션으로 묶는다. 트랜잭션 경계는 화면이 아니라 저장 작업의 일관성 기준으로 정한다.
- 예: 카테고리 삭제와 현재 물품의 미분류 이동, 장보기 완료 기록 생성과 완료 대상의 현재 목록 정리, 카테고리 순서의 일괄 갱신.
- 업무 규칙은 domain에서 정의하고, 원자적인 저장 구현은 data가 책임진다. 여러 Repository 호출을 UseCase에서 순서대로 실행하는 것만으로 트랜잭션이 보장된다고 간주하지 않는다.
- 트랜잭션 안에서 네트워크·사용자 입력 대기·긴 계산을 수행하지 않는다. DB 작업을 짧게 유지하고 실패 시 부분 변경을 남기지 않는다.
- 읽은 뒤 조건을 판단하고 수정하는 작업은 경합을 고려한다. 조건부 SQL·제약·트랜잭션을 사용하고 영향받은 행 수를 확인한다.
- 취소·예외가 트랜잭션의 성공으로 처리되지 않도록 한다. 커밋 전에 DB 오류를 잡아 성공 값을 반환하지 않는다.

## 동시성·중복·수정 충돌

- 하나의 DB 인스턴스나 코루틴 사용만으로 업무 단위의 동시성이 해결된다고 가정하지 않는다. 여러 ViewModel·작업에서 같은 데이터를 변경할 수 있다.
- UI의 저장 중 중복 클릭 방지와 별개로 DB 제약·안정적인 작업 식별자 등 필요한 저장소 수준의 중복 방지 방식을 정한다.
- 현재 필드만 바꾸는 작업은 대상 필드를 갱신한다. 오래된 객체 전체를 저장해 다른 변경을 덮어쓰지 않는다. 구매 여부 변경은 단순 반전보다 원하는 상태를 지정하는 명령을 우선한다.
- 전체 내용 수정처럼 변경 유실 위험이 있는 작업은 필요에 따라 revision 비교 후 갱신하는 낙관적 동시성 제어를 적용한다. 충돌을 감지하면 조용히 덮어쓰지 않고 재조회·재시도·사용자 확인 정책을 정한다.
- 삭제되거나 변경된 항목을 수정할 때의 결과를 Repository 계약에 명시한다. 항목이 없는데 수정 성공으로 표시하거나 암묵적으로 재생성하지 않는다.
- `Mutex`는 같은 프로세스의 메모리 상태를 보호할 필요가 있을 때만 사용한다. DB 제약·트랜잭션을 대체하거나 모든 Repository 작업을 전역 잠금으로 직렬화하지 않는다.
- 자동 재시도는 같은 작업을 다시 실행해도 중복·이중 반영이 없는지 확인한 뒤 적용한다. 무제한 재시도를 하지 않는다.

## 스레드와 코루틴

- UI 스레드에서 동기 DB I/O를 실행하지 않는다. Room의 비동기 DAO와 해당 버전이 지원하는 쿼리 실행 컨텍스트를 사용한다.
- `suspend` 선언 자체가 백그라운드 실행을 보장하지는 않는다. 직접 사용하는 blocking 파일·DB API는 적절한 실행 컨텍스트에서 처리한다.
- 각 호출마다 스레드·독립 CoroutineScope를 만들거나 `GlobalScope`를 사용하지 않는다. 작업 수명과 취소 책임을 명확히 한다.
- 가변 컬렉션·공유 메모리를 여러 코루틴에서 무방비로 수정하지 않는다. DB 트랜잭션과 메모리 상태 보호의 역할을 구분한다.
- `CancellationException`은 전파한다. 모든 예외를 일반 오류나 빈 목록으로 변환하지 않는다.

## 오류·조회 계약

- 예상 가능한 저장·조회 실패는 기존 domain 결과 계약으로 변환한다. 원본 DB 예외·SQL·플랫폼 경로를 사용자 메시지에 노출하지 않는다.
- 빈 목록, 항목 없음, 중복·수정 충돌, 저장 실패를 계약에 필요한 만큼 구분한다. 조회 실패를 빈 목록으로 숨기지 않는다.
- 관찰 Flow가 실패 시 종료되는지, 재구독이 필요한지는 기존 Repository 계약과 일치시킨다. 무조건적인 retry·catch로 계약을 바꾸지 않는다.
- 저장 성공 안내·화면 이동은 DB 커밋 성공을 확인한 뒤 처리한다. UI의 낙관적 변경을 사용한다면 실패 시 복구 정책을 함께 정의한다.
- 여러 조회 결과를 조합해 같은 시점의 일관성이 필요하면 단일 쿼리나 트랜잭션 조회를 검토한다. 독립 Flow를 합친 것만으로 동일 스냅샷이 보장되지는 않는다.

## 스키마와 마이그레이션

- 초기 스키마부터 버전을 부여하고 Room의 내보낸 스키마와 마이그레이션 코드를 저장소에서 관리한다. 일반 build 산출물과 구분한다.
- 스키마 변경 시 기존 데이터 변환·기본값·null·인덱스·외래키와 지원 버전의 업그레이드 경로를 검토한다. UI·로직 변경만으로 DB 버전을 올리지 않는다.
- 실제 사용자 데이터에 파괴적 마이그레이션이나 오류 시 DB 삭제를 기본값으로 사용하지 않는다. 개발용 초기화는 폐기 가능한 데이터에만 명시적으로 적용한다.
- 자동 마이그레이션이 지원하는 변경인지 확인하고, 데이터 변환이나 이름 변경 등 추가 처리가 필요하면 명시적으로 구현한다.
- 일시적인 읽기 오류를 데이터 손상으로 단정하지 않는다. 손상·복구 불가 상황은 오류를 보고하고 복구 정책을 논의한다.

## 향후 서버·공유와의 경계

- 로컬 트랜잭션은 다른 기기·서버와의 원자성이나 동시 편집을 보장하지 않는다. 서버 측 권한·버전 검사·충돌 해결은 별도 설계한다.
- 로컬 데이터 revision과 서버 버전을 혼용하지 않는다. 기기 시각의 `updatedAt`만으로 변경 순서나 충돌 해결을 보장하지 않는다.
- 삭제 전파, 변경 큐·outbox, 재시도 중복 방지는 실제 동기화 도입 시 필요한 범위로 설계한다. `deletedAt` 필드만 추가하고 동기화가 해결되었다고 간주하지 않는다.
- 로컬 저장만 구현된 단계에서는 사용자 간 공유·편집자 표시·실시간 동기화가 동작한다고 안내하지 않는다.

## 변경 후 확인

- 변경한 기능에 맞춰 재실행 후 데이터 유지, CRUD·기간 조회, 과거 기록 보존, 중복 요청·충돌·실패 시 부분 저장 여부를 확인한다.
- 스키마 변경은 기존 스키마에서 업그레이드 후 데이터가 보존되는지 확인한다. 새 DB 생성만 확인하고 마이그레이션 검증을 대체하지 않는다.
- 공통·플랫폼 코드 변경에 맞는 Android·iOS 빌드를 선택해 확인하고 불필요하게 반복하지 않는다. 실행하지 못한 환경과 검증 범위는 보고한다.
- 테스트 코드 추가·수정은 루트 [AGENTS.md](../../AGENTS.md)의 사용자 요청 기준을 따른다. 문서만 변경했다면 링크·일관성만 확인하고 앱 빌드는 실행하지 않는다.
