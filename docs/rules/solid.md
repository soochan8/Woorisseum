# SOLID와 단순한 설계 규칙

## 적용 범위

Kotlin 운영 코드의 설계, 기능 구현과 리팩토링 전반에 적용한다.
SOLID를 이유로 현재 요구에 없는 계층·인터페이스·상속 구조를 추가하지 않는다.

## SOLID 적용

| 원칙 | 적용 규칙 | Woorisseum 예시 |
| --- | --- | --- |
| SRP: 단일 책임 | 함께 변경되는 책임을 모으고, 서로 다른 변경 이유는 분리한다. | ViewModel은 Intent·화면 상태, Repository 구현은 데이터 접근, Mapper는 타입 변환을 담당한다. |
| OCP: 개방·폐쇄 | 변화가 예상되는 경계에 계약을 두어 구현 교체의 영향을 줄인다. | 저장 방식 변경을 domain Repository 계약 뒤에 숨긴다. 모든 변경을 확장으로 처리할 필요는 없다. |
| LSP: 리스코프 치환 | 구현을 바꿔도 호출자가 기대하는 계약을 유지한다. | 같은 Repository 계약의 빈 결과·실패·정렬·취소 의미가 구현마다 달라지지 않게 한다. |
| ISP: 인터페이스 분리 | 호출자가 사용하지 않는 책임까지 의존하지 않게 한다. | 관련 없는 인증·거래·장보기 기능을 거대한 단일 Repository에 넣지 않는다. |
| DIP: 의존 역전 | 상위 정책은 외부 구현 세부사항보다 계약에 의존한다. | feature는 domain Repository 인터페이스를 사용하고 shared가 data 구현을 연결한다. |

## KISS·YAGNI·DRY

- KISS: 현재 요구를 충족하는 가장 이해하기 쉬운 구조를 선택한다. 읽기 어려운 범용화와 불필요한 간접 계층을 피한다.
- YAGNI: 미래에 쓸 것 같다는 이유만으로 기능·모듈·프레임워크를 미리 만들지 않는다.
- DRY: 같은 비즈니스 규칙과 지식의 중복을 줄인다. 코드 모양만 비슷하고 변경 이유가 다르면 억지로 공통화하지 않는다.
- 인터페이스는 계약·교체 경계가 필요할 때 만든다. 모든 클래스에 대응하는 인터페이스를 만들지 않는다.
- 공통 코드의 응집도를 먼저 확인한다. feature 전용 코드를 단지 여러 줄 반복된다는 이유로 designsystem이나 공용 유틸에 옮기지 않는다.
- 상속보다 명시적인 구성과 생성자 주입을 우선 검토한다. 요구가 없는 `BaseViewModel`·`BaseRepository`를 만들지 않는다.
- 파일 수를 줄이거나 늘리는 것 자체를 목표로 하지 않는다. 비즈니스 책임과 이해 가능한 변경 범위를 기준으로 나눈다.

## 적용 방법

1. 현재 변경이 필요한 책임과 변경 이유를 한 문장으로 정리한다.
2. 기존 타입과 계약으로 해결할 수 있는지 확인한다.
3. 별도 추상화가 필요하면 실제 호출자, 교체 지점, 유지해야 할 계약을 정한다.
4. 추상화를 추가하는 비용보다 변경 영향과 중복을 줄이는 효과가 큰지 판단한다.
5. 현재 요구를 설명할 수 없는 계층·옵션·확장 지점은 추가하지 않는다.

## 피해야 할 해석

- 단일 책임을 지키려고 관련된 동작을 무조건 여러 클래스로 쪼개기.
- OCP를 이유로 기존 코드는 수정할 수 없다고 판단하기.
- DI 컨테이너를 사용한다는 사실만으로 의존 역전을 지켰다고 판단하기.
- 단순 위임 UseCase·한 구현만 감싸는 불필요한 인터페이스를 일괄 생성하기.
- 규칙을 이유로 요청 범위 밖의 전체 구조를 함께 리팩토링하기.

## 완료 전 확인

- 타입과 함수의 책임을 명확히 설명할 수 있는가?
- 구현을 바꾸면 실제로 관계없는 영역까지 수정해야 하는가?
- 공통화된 코드는 같은 이유로 함께 바뀌는가?
- 더 단순한 구현으로 같은 요구와 모듈 경계를 만족할 수 있는가?
