# 함께 쓰기 서버 데이터 구조와 초대 정책

## 상태와 범위

2026-11-26 기준 이슈 #9의 테이블·초대 정책 설계다. API 계약까지 정의했고, 테이블·제약·조회 RLS의 1차 SQL 파일을 작성했다. 사용자 실행 결과로 1차 테이블 4개·RLS 활성화를 확인했다. 사용자 확인으로 2차 프로필·상태 조회 RPC 적용도 확인했다. 초대 RPC 3차 SQL도 사용자 적용 확인을 받았다. 앱의 프로필 저장·수정·상태 조회·재진입 복원을 연결했고, 초대 작업의 앱 연결은 아직 진행하지 않았다.

- 구현 완료: Supabase 익명 인증, Android Keystore 암호화·iOS Keychain 세션 보관, 함께 쓰기 입력 UI와 Preview.
- 1차 적용 확인: [테이블·RLS SQL](../supabase/migrations/20261126000100_household_schema.sql). 사용자 제공 실행 결과에서 네 테이블의 RLS 활성화를 확인했다. 접근 권한·제약은 임시 PostgreSQL에서 검증했다.
- 2차 적용 확인: [프로필·상태 조회 SQL](../supabase/migrations/20261126000200_household_profile_state.sql). 사용자가 인증 사용자 실행 허용·미인증 실행 차단 결과를 확인했다.
- 3차 적용 확인: [초대 SQL](../supabase/migrations/20261126000300_household_invitations.sql). 발급·확인·수락 RPC와 실행 권한이 사용자 실행 결과로 확인됐다.
- 앱 연결 완료: 프로필 저장·수정·상태 조회·저장 실패와 후속 조회 실패 구분·수정 충돌 시 초안 보존. 실제 서버 저장·재실행 복원은 Android 공통 구현에서 확인했고 iOS는 빌드·실행을 확인한다.
- 미구현: 앱의 초대 서버 데이터 연결, 초대 URL 생성·공유·플랫폼 링크 진입.
- 이번 문서는 서버 설계다. Room DB 버전·테이블·기존 기록을 변경하지 않는다.
- API 입출력·오류 계약은 [함께 쓰기 API 계약](household-api-contract.md)에 정의했다. 1~3차 SQL을 로컬 PostgreSQL 17.12에서 실행했고, 실제 다중 연결의 초대 경합을 검증했다. 초대 앱 연결은 다음 단계다.

설계는 [아키텍처](rules/architecture.md)와 [클린 아키텍처](rules/clean-architecture.md)를 따른다. 로컬 기록의 현재 범위는 [로컬 DB 설계](local-database-design.md)를 참고한다.

## 확정 정책

| 항목 | 규칙 |
| --- | --- |
| 사용자 식별 | Supabase Auth 사용자 UUID를 사용한다. 익명 인증 사용자도 서로 다른 ID를 가진다. |
| 프로필 | 이름과 기본 이모지를 저장한다. 인증 자격 증명·초대 토큰은 프로필에 저장하지 않는다. |
| 혼자 사용 | 기존 개인 사용 기능을 유지한다. 함께 쓰기를 사용하지 않는다고 기록을 제한하지 않는다. |
| 공유 공간 수 | 사용자당 동시에 하나의 공유 공간에만 속한다. |
| 구성원 수·권한 | 최대 2명이며 연결 후 권한은 동등하다. 최초 생성자는 소유자·관리자 권한을 갖지 않는다. |
| 초대 만료 | 서버 발급 시각부터 24시간이다. `현재 시각 >= expires_at`이면 만료다. |
| 재발급 | 새 링크 발급과 기존 미사용 링크 무효화를 한 트랜잭션으로 처리한다. 새 링크만 사용할 수 있다. |
| 초대 사용 | 한 번만 수락할 수 있다. 확인 화면을 여는 것만으로 사용 처리하거나 자리를 예약하지 않는다. |
| 본인 초대 | 자신이 발급한 초대에는 참여할 수 없다. |
| 수락 확정 | 서버 트랜잭션 커밋 이후에만 연결 완료로 표시한다. |
| 서로 초대 | 두 사람 모두 초대했어도 한쪽을 수락하면 하나의 공간으로 연결한다. 두 사람의 남은 미사용 초대는 무효화한다. |
| 기존 기록 | 연결 시 로컬 지출·카드·예산·고정지출·장보기를 업로드·이동·삭제하지 않는다. |
| 연결 해제·복구 | 이번 범위에 없다. 탈퇴·재연결·계정 삭제·기기 변경 복구는 별도 정책과 구현이 필요하다. |

이름은 앞뒤 공백을 정리하고 빈 값은 거부한다. 이름·이모지가 같아도 동일 사용자로 판단하지 않는다. 표시 이름의 중복을 금지하지 않으며 사용자 구분은 UUID로 한다. API 계약 단계에서 사용자 확인을 거쳐 공백 정리 후 1~30 Unicode 코드포인트로 제한했다. 공백 정리 집합과 앱·서버의 동일 적용 기준은 API 계약을 따른다.

## 테이블 관계

| 관계 | 의미 |
| --- | --- |
| `auth.users.id` → `profiles.user_id` | 인증 사용자 한 명에 프로필 하나. 프로필은 함께 쓰기 설정 시 명시적으로 생성·수정한다. |
| `profiles.user_id` → `household_members.user_id` | 프로필 하나는 현재 구성원 행을 최대 하나만 가진다. |
| `households.id` → `household_members.household_id` | 한 공간에 구성원은 최대 두 명이다. |
| `households.id` → `household_invitations.household_id` | 초대는 정확히 하나의 공간을 대상으로 발급한다. |
| `profiles.user_id` → 초대의 발급자·수락자 | 누가 발급·수락했는지 기록한다. |

`auth.users`는 Supabase가 관리한다. 별도 사용자 비밀번호 테이블을 만들지 않는다. 아래 네 테이블만 새로 설계한다.

## 1. profiles — 표시 프로필

| 컬럼 | 타입·필수 여부 | 의미·제약 |
| --- | --- | --- |
| `user_id` | uuid, 필수 | PK, `auth.users.id` 참조. 다른 사용자의 ID로 프로필을 생성할 수 없다. |
| `display_name` | text, 필수 | 공백 정리 후 빈 값 금지. 중복 허용. |
| `emoji_code` | text, 필수 | 안정적인 저장 코드. `CAT`, `DOG`, `RABBIT`, `BEAR`, `FOX`, `PANDA`, `FROG`, `PENGUIN` 중 하나. |
| `created_at` | timestamptz, 필수 | 서버 생성 시각. |
| `updated_at` | timestamptz, 필수 | 서버에서 갱신하는 수정 시각. |
| `revision` | bigint, 필수 | 초기값 1, 양수 제약. 실제 프로필 수정마다 증가하며 서버의 동시 수정 검사에 사용한다. 로컬 데이터 revision과 구분한다. |

- 이모지 글리프·enum ordinal을 서버 식별 코드로 사용하지 않는다. 앱 Mapper에서 기존 이모지 선택값과 변환한다.
- 같은 공간의 상대에게 보여줄 정보는 표시 이름·이모지로 제한한다. 이메일·세션 토큰을 함께 반환하지 않는다.
- 프로필 저장만으로 공간 생성이나 연결 완료를 의미하지 않는다.

## 2. households — 공유 공간

| 컬럼 | 타입·필수 여부 | 의미·제약 |
| --- | --- | --- |
| `id` | uuid, 필수 | 서버에서 발급하는 PK. |
| `created_by` | uuid, 필수 | `profiles.user_id` 참조. 생성 경위 기록이며 권한 구분이 아니다. |
| `created_at` | timestamptz, 필수 | 서버 생성 시각. |
| `closed_at` | timestamptz, 선택 | 비어 있는 1인 준비 공간을 정리한 시각. null이면 열린 공간이다. |

- 첫 초대 발급 시 아직 공간이 없다면 공간·본인 구성원·초대를 함께 생성한다. 발급 실패로 빈 공간만 남지 않도록 한다.
- 초대받는 사람은 링크를 확인하는 것만으로 별도 공간을 만들지 않는다.
- 연결 여부는 열린 공간의 현재 구성원 두 명으로 판단한다. 별도 `is_connected` 플래그를 중복 저장하지 않는다.
- 공간을 닫는 것은 물리 삭제나 로컬 기록 삭제를 의미하지 않는다. 닫힌 공간에는 참여·초대 발급을 허용하지 않는다.

## 3. household_members — 현재 구성원

| 컬럼 | 타입·필수 여부 | 의미·제약 |
| --- | --- | --- |
| `user_id` | uuid, 필수 | PK, `profiles.user_id` 참조. 사용자당 현재 공간 하나를 보장한다. |
| `household_id` | uuid, 필수 | `households.id` 참조. |
| `slot` | smallint, 필수 | 1 또는 2만 허용한다. |
| `joined_at` | timestamptz, 필수 | 서버가 참여를 확정한 시각. |

- `CHECK(slot IN (1, 2))`와 `UNIQUE(household_id, slot)`을 함께 둔다. 공간당 두 자리를 넘는 행을 DB 제약으로 차단한다.
- slot은 내부 자리 식별자다. 소유자·참여자 권한, 화면 순서, 지출 주체를 의미하지 않는다.
- 이 테이블은 현재 구성원 관계다. 탈퇴 이력이나 회계 기록의 작성자 이력을 대신하지 않는다.
- 구성원 추가·이동·삭제는 서버 업무 처리로 제한한다. 앱이 직접 행을 추가해 초대 수락을 우회할 수 없게 한다.
- 사용자별 PK 조회와 공간별 복합 UNIQUE 인덱스를 사용한다. 같은 목적의 중복 인덱스를 추가하지 않는다.

## 4. household_invitations — 초대와 처리 결과

| 컬럼 | 타입·필수 여부 | 의미·제약 |
| --- | --- | --- |
| `id` | uuid, 필수 | 서버 발급 PK. 링크의 비밀 토큰과 구분한다. |
| `household_id` | uuid, 필수 | 대상 `households.id` 참조. |
| `created_by` | uuid, 필수 | 발급한 `profiles.user_id` 참조. |
| `create_request_id` | uuid, 필수 | 발급 동작의 중복 전송 식별자. `(created_by, create_request_id)` UNIQUE. |
| `token_hash` | bytea, 필수 | base64url 토큰을 복원한 원본 32바이트의 SHA-256 해시. UNIQUE, 길이 32바이트. 원본 토큰은 DB에 저장하지 않는다. |
| `created_at` | timestamptz, 필수 | 서버 발급 시각. |
| `expires_at` | timestamptz, 필수 | 발급 시각 + 24시간. 서버가 설정한다. |
| `accepted_by` | uuid, 선택 | 수락한 `profiles.user_id` 참조. |
| `accepted_at` | timestamptz, 선택 | 수락 확정 시각. |
| `revoked_at` | timestamptz, 선택 | 재발급·공간 정리·연결 완료로 무효화한 시각. |

저장 제약과 취급:

- `accepted_by`와 `accepted_at`은 함께 null이거나 함께 값이 있어야 한다.
- 발급자와 수락자는 같을 수 없다. 수락된 초대와 무효화된 초대가 동시에 되지 않도록 한다.
- 발급·만료·수락·무효화 시각의 선후 관계를 검사한다. 기기 시각을 신뢰하지 않는다.
- 공간당 수락·무효화되지 않은 초대 한 개만 있도록 부분 UNIQUE 인덱스를 둔다. 시간 조건을 인덱스 조건에 넣지 않는다. 만료된 미처리 초대도 재발급 시 명시적으로 무효화한다.
- 토큰 해시 UNIQUE는 링크 확인 조회에도 사용한다. 사용자·초대 토큰 목록을 외부에 공개하지 않는다.
- 원본 토큰은 서버에서 암호학적으로 안전한 256비트 난수로 생성하고 URL에 사용할 수 있게 인코딩한다. 링크를 가진 사람의 참여 권한으로 취급하며 로그·분석 이벤트에 기록하지 않는다.
- 원본 링크는 발급 응답으로만 제공한다. 발급 응답을 잃거나 앱을 재시작해 원본 링크가 없으면 재발급한다. 기존 링크를 해시에서 복원하지 않는다.
- 네트워크 자동 재시도로 초대를 반복 재발급하지 않는다. 동일 발급 요청 ID는 중복 부수효과를 차단하지만 원본 링크 응답은 재생하지 않는다. 결과 유실·재발급 처리는 API 계약을 따른다.

상태는 시각·처리 결과로 계산한다. 별도 만료 상태 컬럼이나 만료 예약 작업이 있어야만 만료되는 구조를 만들지 않는다.

| 판정 | 의미 |
| --- | --- |
| `accepted_at` 있음 | 사용 완료. 같은 수락자의 응답 유실 재시도는 현재 구성원 관계까지 검증해 기존 성공을 반환할 수 있다. |
| `revoked_at` 있음 | 무효화됨. 이전 링크로 참여할 수 없다. |
| 서버 현재 시각 ≥ `expires_at` | 만료됨. |
| 그 외 | 수락 검증 후보. 대상 공간·구성원·본인 여부를 추가 확인해야 한다. |

연결된 공간은 미사용 초대를 함께 무효화한다. 정원 초과는 수락 시에도 방어적으로 검사하지만, 누구나 공간을 조회해 인원수를 확인하게 만들지는 않는다.

## 서로 초대한 경우와 원자성

A·B가 각각 1인 준비 공간과 초대를 만든 뒤, B가 A의 링크를 수락하는 경우:

1. 인증된 B와 토큰의 발급자·대상 공간을 확인한다. 요청 본문의 사용자 ID를 인증 주체로 신뢰하지 않는다.
2. 참여에 관련된 사용자·공간·초대 변경을 일관된 순서로 잠그고, 잠금 뒤 최신 상태와 서버 시각으로 다시 검증한다.
3. B가 속한 공간이 없다면 A의 빈 자리에 참여시킨다.
4. B에게 공간이 있다면 **B만 속한 비어 있는 1인 준비 공간**인 경우에만 이전 미사용 초대를 무효화하고, 이전 구성원 관계를 정리한 뒤 그 공간을 닫는다.
5. B를 A의 공간에 추가하고 A의 해당 초대를 사용 완료로 기록한다. 연결된 공간의 다른 미사용 초대도 무효화한다.
6. 하나의 트랜잭션으로 커밋한다. 어느 단계라도 실패하면 준비 공간·구성원·초대 변경을 모두 롤백한다.

여기서 비어 있음은 서버 업무 데이터가 없다는 뜻이다. 현재는 서버 업무 테이블이 없지만, 지출·장보기 등 서버 저장을 도입할 때에는 이 조건을 함께 확장해야 한다. 서버 업무 데이터가 있는 공간을 자동 병합·폐쇄하지 않는다. 로컬 기록의 존재 여부는 이 정리 조건이 아니며 로컬 기록은 건드리지 않는다.

동시성 정책:

- 서로의 초대를 동시에 수락하면 먼저 커밋된 연결만 유지한다. 뒤의 요청은 최신 관계를 재조회해 이미 연결됨을 안내하며 두 번째 이동을 수행하지 않는다.
- 같은 링크를 서로 다른 두 사용자가 동시에 수락해도 한 명만 성공해야 한다.
- 같은 사용자가 다른 링크를 동시에 수락해도 현재 공간이 두 개 생기면 안 된다.
- 발급·재발급·수락에서 동일 사용자·공간을 잠그는 순서를 통일한다. 사용자 잠금은 2차 SQL의 비공개 `lock_users(uuid[])`를 공유한다. `hashtextextended('woorisseum:user:' || UUID, 0)`의 중복 제거된 bigint 키를 오름차순으로 잠그는 트랜잭션 advisory lock이다. 3차 수락 함수는 관련 사용자 키 → 공간 UUID 오름차순 → 초대 UUID 오름차순으로 잠그며 발급 함수도 같은 선행 순서를 따른다.
- 재발급과 수락이 겹치면 먼저 확정된 결과를 기준으로 재검증한다. 무효화된 링크는 성공시킬 수 없다.
- 동일 수락 요청의 재전송은 현재 구성원 관계와 사용 완료 기록을 확인한다. 같은 참여 결과를 유지하며 다른 사용자의 수락으로 덮어쓰지 않는다.

최대 2명·사용자당 공간 하나는 DB 제약으로도 방어하며, 토큰 유효성·권한·준비 공간 이동은 서버 트랜잭션에서 처리한다. 클라이언트 Mutex나 RLS만으로 이 규칙을 보장했다고 간주하지 않는다.

## 접근 권한 설계의 입력

1차 SQL은 아래 경계의 조회 RLS와 직접 쓰기 차단을 구현한다. 2차 SQL은 프로필 저장·상태 조회 RPC와 실행 권한을 구현한다. 3차 SQL은 초대 발급·확인·수락 RPC와 인증 사용자 전용 실행 권한을 구현한다.

- 프로필은 본인이 생성·수정한다. 조회는 본인·같은 공간의 상대에게 필요한 범위로 제한한다.
- 공간·구성원 조회는 해당 공간의 구성원에게만 허용한다.
- 초대의 원본 행·토큰 해시 조회와 구성원 직접 변경을 앱에 개방하지 않는다.
- 유효한 토큰으로 초대를 확인한 인증 사용자에게만 초대한 사람의 표시 정보를 제한적으로 제공한다. 무효한 링크로 상대 정보를 얻을 수 없어야 한다.
- 발급·확인·수락은 서버가 인증 주체·권한·최신 상태를 확인한다. 권한이 높은 함수가 필요한 경우 호출 권한과 함수 내부 검증도 별도로 제한한다.
- 외래키 삭제는 기본적으로 RESTRICT/NO ACTION을 사용한다. auth 사용자·프로필·공간 삭제가 다른 사람의 관계·기록을 암묵적으로 연쇄 삭제하지 않도록 한다. 실제 계정 삭제 경로는 별도 설계한다.

## 구현 전 확인 시나리오

아래는 다음 구현 단계의 검증 기준이다. 이번 문서 작업에서 실행했다는 뜻이 아니다.

| 상황 | 기대 결과 |
| --- | --- |
| A 초대 → B 확인 | A의 표시 프로필만 확인하며 구성원은 아직 1명이다. |
| B 수락 | A·B가 같은 공간에 속하고 링크는 사용 완료가 된다. |
| 24시간 경계 | 정확히 만료 시각부터 수락을 거절한다. 잠금 대기 후에도 다시 검사한다. |
| 재발급 후 이전 링크 사용 | 이전 링크는 무효, 새 링크만 수락 가능하다. |
| 본인 초대 수락 | 구성원·초대를 변경하지 않고 거절한다. |
| C·D가 같은 링크 동시 수락 | 한 명만 성공하며 구성원 수는 2명을 넘지 않는다. |
| A·B가 서로 초대한 뒤 동시 수락 | 하나의 연결만 유지하고 불필요한 1인 준비 공간만 닫는다. |
| 이미 연결된 사용자의 다른 공간 참여 | 현재 연결을 유지하고 요청을 거절한다. |
| 수락 성공 응답 유실 후 같은 사용자가 재시도 | 구성원 중복 생성 없이 기존 참여 결과를 확인한다. |
| 토큰·공간 ID 변조 | 다른 사람의 프로필·공간·초대 목록을 노출하거나 변경하지 않는다. |
| 참여 처리 중 오류 | 이전 공간·구성원·초대 상태가 부분 변경되지 않는다. |
| 연결 전후 앱 재실행 | 서버 관계를 복원하며 기존 로컬 기록은 보존한다. |
